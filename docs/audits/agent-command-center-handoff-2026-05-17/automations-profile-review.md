## Summary

This continuation picked up after `/today` and `/agent` were accepted for the current V1 Agent Command Center migration stage.

The next unfinished V1 surfaces were `/automations` and `/profile`. Both previously existed as static explanatory pages. This pass turned them into richer product workspaces while keeping the current backend limitation explicit: durable automation settings and profile writeback confirmations are not yet backed by dedicated tables/endpoints.

## Rework Completed

- Added `AutomationsWorkspace` as a client workspace for `/automations`.
- `/automations` now shows:
  - Daily Brief automation as default-on.
  - Weekly Portfolio Check, News Impact Watch, and Behavior Bias Observation as controllable authorization cards.
  - Per-card read scope, generated output, cadence, confirmation boundary, and safety boundary.
  - A local switch interaction for authorization intent.
  - A run queue summary based on currently enabled cards.
  - Current Daily Brief headline, last generated time, and source coverage count when dashboard state is available.
- Added `ProfileWorkspace` as a client workspace for `/profile`.
- `/profile` now shows:
  - context completeness across profile, risk, portfolio, news, learning, simulation, and behavior sources,
  - risk profile and behavior focus,
  - latest portfolio context,
  - learning and simulation state,
  - pending writeback cards with source, evidence, writeback type, and explicit user decision controls,
  - data authorization/readiness scope.
- Updated focused web e2e coverage:
  - `/automations` exposes controllable safe automation settings,
  - `/profile` keeps context and writebacks confirmable.
- Fixed `ProgressBar` accessibility by adding an accessible progressbar name.

## Acceptance

`/automations` and `/profile` are acceptable for the current V1 frontend migration stage.

Follow-up backend continuation:

- `20260517_0010` added durable `automation_settings`, `automation_runs`, and `daily_brief_preferences`.
- `GET /api/automations`, `PATCH /api/automations/{automation_key}`, and `POST /api/automations/{automation_key}/run` now provide the first backend-owned automation contract.
- `GET /api/profile/context`, `GET /api/profile/pending-proposals`, `POST /api/profile/pending-proposals/{proposal_id}/accept`, and `POST /api/profile/pending-proposals/{proposal_id}/reject` now provide the first profile context and pending writeback contract.
- Pending writebacks reuse `agent_state_update_proposals` with explicit user-decision fields instead of creating a duplicate proposal table.
- Follow-up frontend API connection is now complete in `frontend-api-connection-review.md`: `/automations` and `/profile` consume these backend contracts instead of local seed state.

Residual product/backend limitations:

- Automation runs are synchronous manual records, not a scheduler or background worker.
- Profile proposal application is allow-listed; current target application covers confirmed `behavior_profile_note` only.

Recommended next backend contract:

```text

PATCH /api/automations/{automation_key}
POST  /api/automations/{automation_key}/run

GET   /api/profile/context
GET   /api/profile/pending-proposals
POST  /api/profile/pending-proposals/{proposal_id}/accept
POST  /api/profile/pending-proposals/{proposal_id}/reject
```
